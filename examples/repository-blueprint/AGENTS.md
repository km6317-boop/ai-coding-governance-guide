# Repository Working Agreement

이 파일은 도구 중립적인 저장소 지침의 단일 원본이다. 특정 AI 제품의 명령, 모델 이름, 개인 취향은 넣지 않는다.

## 1. 적용 범위와 기준 자료

- 플랫폼의 보안 정책과 사용자의 현재 명시적 요청을 항상 우선한다.
- 작업을 시작할 때 저장소 루트, 현재 브랜치/worktree, 변경된 파일을 읽기 전용으로 확인한다.
- 비어 있지 않은 기존 변경은 사용자의 작업으로 간주한다. 요청 범위 밖의 변경을 되돌리거나 덮어쓰지 않는다.
- 비사소한 변경에서 Spec Kit가 설치되어 있다면 현재 constitution, feature spec, plan, tasks를 먼저 읽는다.
- 장기 아키텍처, 정책, 결정은 `knowledge/index.md`에서 필요한 문서만 찾아 읽는다.
- 충돌이 있으면 추측으로 조용히 선택하지 말고 충돌한 파일과 선택이 필요한 이유를 보고한다.

## 2. 작업 분리

- 이슈 하나당 브랜치 하나, AI 작업 하나당 Git worktree 하나를 사용한다.
- 둘 이상의 작업자가 같은 worktree를 동시에 수정하지 않는다.
- 할당된 파일과 task 범위만 수정한다. 다른 작업의 코드를 선제적으로 정리하지 않는다.
- 공유 파일 수정이 겹치면 병렬로 진행하지 말고 소유자와 순서를 정한다.

## 3. 구현 절차

1. 요청, 활성 spec, 관련 코드와 테스트를 읽고 성공 조건을 한 문장으로 정리한다.
2. 가장 작은 안전한 변경을 설계한다.
3. 동작이 바뀌면 먼저 또는 함께 테스트를 추가·수정한다.
4. 저장소에 이미 정의된 formatter, lint, typecheck, test, build 명령을 사용한다.
5. 실패를 숨기거나 우회하지 않는다. 원인과 남은 위험을 기록한다.
6. diff를 검토하여 범위 밖 변경과 생성물을 제거한다.

프로젝트 명령이 아직 문서화되지 않았다면 package manifest, build 파일, CI workflow에서 근거를 찾는다. 확인할 수 없는 명령을 꾸며내지 않는다.

## 4. Spec과 지식

- `specs/`는 현재 feature의 요구사항, 계획, 작업과 검증 기준을 담는다.
- `knowledge/`는 여러 feature에서 재사용할 아키텍처, 정책, 결정, runbook을 담는다.
- 같은 내용을 두 곳에 복제하지 말고 서로 링크한다.
- OKF concept를 바꾸면 근거인 `sources`, 생성 시각, `stale_after`, 관련 `knowledge/log.md`를 함께 검토한다.
- 사람 검토가 없었으면 `verified: human:...`을 추가하지 않는다.

## 5. 보안과 외부 변경

- API key, token, password, private key, 개인 인증 캐시를 읽거나 커밋하지 않는다.
- `.env`, `secrets/`, 개인 설정 파일이 필요하면 값이 아닌 변수 이름과 설정 방법만 문서화한다.
- 새 production dependency, 권한 확대, 외부 MCP/Plugin/Skill/Hook 설치는 사람의 검토와 승인을 받는다.
- push, force-push, PR merge, release, package publish, deploy, production 변경은 **해당 동작에 대한 사용자의 명시적 승인** 없이는 실행하지 않는다.
- 비대화형 환경에서는 승인할 사람이 없으므로 위 외부 동작을 거부한다.
- 파괴적 파일 작업, 이력 재작성, 운영 데이터 변경은 정확한 대상과 복구 방법을 확인하고 별도 승인을 받는다.

## 6. Git 규칙

- 사용자가 요청하지 않으면 commit, tag, push, merge를 만들지 않는다.
- `main` 또는 보호 브랜치에 직접 작업하지 않는다.
- force-push와 보호 브랜치 삭제는 금지한다.
- commit을 요청받으면 한 가지 논리적 변경만 담고 테스트 증거를 남긴다.

## 7. 완료 조건

완료를 선언하려면 다음을 모두 만족한다.

- 요청과 활성 spec의 acceptance criteria를 충족했다.
- 관련 테스트와 저장소 표준 검사가 통과했다.
- 실행한 검증 명령과 결과를 보고했다.
- 최종 diff에 비밀값, 디버그 파일, 범위 밖 변경이 없다.
- 필요한 문서와 장기 지식이 코드와 일치한다.
- 실패하거나 실행하지 못한 검증을 명확히 밝혔다.

AI 설정 또는 Skill을 바꿨다면 `node scripts/verify-ai-config.mjs`도 실행한다.

## Code Review Rules

- 요구사항 누락, 회귀, 보안 경계 약화, 오류 처리 부재, 테스트 공백을 우선 검토한다.
- 스타일만으로 변경을 확대하지 않는다. 자동 검사로 확인할 수 있는 형식 문제는 해당 검사 결과를 근거로 한다.
- finding에는 영향을 받는 경로, 재현 조건, 기대 동작을 포함한다.
