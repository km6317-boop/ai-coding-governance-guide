# Repository Working Agreement

이 파일은 저장소에서 사용하는 모든 코딩 AI가 함께 지킬 도구 중립 규칙의 단일 원본이다.

## 범위와 기준 자료

- 플랫폼 정책과 사용자의 현재 명시적 요청을 최우선으로 따른다.
- 시작할 때 저장소 루트, 현재 브랜치 또는 worktree, 기존 변경을 읽기 전용으로 확인한다.
- 기존 변경은 사용자의 작업으로 간주하고 요청 범위 밖 파일을 되돌리거나 덮어쓰지 않는다.
- Spec Kit가 설치되어 있으면 현재 constitution과 활성 feature의 `spec.md`, `plan.md`,
  `tasks.md`에서 이번 변경의 범위와 수용 기준을 확인한다.
- 장기 아키텍처·정책·결정은 `knowledge/index.md`에서 필요한 OKF 문서만 찾아 읽는다.
- 요청, 활성 spec, 저장소 지침이 충돌하면 임의로 선택하지 말고 충돌과 필요한 결정을 알린다.

## 작업과 구현

- 이슈 하나당 브랜치 하나, AI 작업 하나당 Git worktree 하나를 사용한다.
- 같은 worktree를 여러 작업자가 동시에 수정하지 않는다.
- 할당된 파일과 task만 수정하고 관련 없는 리팩터링을 섞지 않는다.
- 동작이 바뀌면 테스트를 먼저 또는 함께 변경한다.
- 저장소가 정의한 formatter, lint, typecheck, test, build 명령을 사용한다.
- 실패를 숨기거나 우회하지 않고 원인과 남은 위험을 기록한다.
- 마지막에 diff를 검토하여 범위 밖 변경, 생성물, 비밀값이 없는지 확인한다.

## 사양과 지식

- `specs/`에는 현재 feature의 요구사항·계획·작업·검증 기준을 둔다.
- `knowledge/`에는 여러 feature에서 재사용할 아키텍처·정책·결정·runbook을 둔다.
- 같은 내용을 두 곳이나 AI별 지침 파일에 복제하지 말고 링크한다.
- OKF concept를 바꾸면 `sources`, 생성 시각, `stale_after`, `knowledge/log.md`를 검토한다.
- 사람 검토가 없었다면 `verified: human:...` 신호를 추가하지 않는다.

## 보안과 외부 변경

- API key, token, password, private key, 인증 캐시를 읽거나 커밋하지 않는다.
- `.env`, 비밀 저장소, 개인 설정은 값이 아니라 필요한 변수 이름과 설정 방법만 문서화한다.
- 새 production dependency, 권한 확대, 외부 MCP·Plugin·Skill·Hook 설치는 사람 검토를 받는다.
- push, force-push, merge, release, publish, deploy, 운영 변경은 해당 동작에 대한 명시적
  요청이나 승인 없이 실행하지 않는다.
- 파괴적 파일 작업, 이력 재작성, 운영 데이터 변경은 정확한 대상과 복구 방법을 먼저 확인한다.

## 프로젝트 명령

아래 값은 저장소의 manifest, build 파일, CI workflow를 근거로 채운다. 확인할 수 없는
명령을 꾸며내지 않는다.

- 설치: `[프로젝트에 맞게 변경]`
- 빠른 검사: `[프로젝트에 맞게 변경]`
- 전체 테스트: `[프로젝트에 맞게 변경]`
- 빌드: `[프로젝트에 맞게 변경]`
- AI 설정 검사: `node scripts/verify-ai-config.mjs` `[해당 스크립트가 있을 때만]`

## 완료 조건

- 요청과 활성 spec의 수용 기준을 충족했다.
- 관련 테스트와 저장소 표준 검사가 통과했다.
- 실행한 검증 명령과 결과를 보고했다.
- 최종 diff에 비밀값, 디버그 파일, 범위 밖 변경이 없다.
- 필요한 문서와 장기 지식이 코드와 일치한다.
- 실행하지 못했거나 실패한 검증과 남은 위험을 명확히 밝혔다.

## 코드 리뷰

- 요구사항 누락, 회귀, 보안 경계 약화, 오류 처리 부재, 테스트 공백을 우선 검토한다.
- 스타일만으로 변경을 확대하지 않는다.
- finding에는 영향 경로, 재현 조건, 기대 동작을 포함한다.
