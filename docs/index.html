먼저, 이름과 역할부터 정확히

비슷해 보이는 파일도 역할이 다릅니다. 지침·설정·절차·외부 도구·지식을 분리하면 세 AI를 함께 써도 규칙이 꼬이지 않습니다.

“Google OFK” → “Google Cloud OKF”

이 문맥의 공식 명칭은 OKF(Open Knowledge Format)입니다. Google 공식 자료에서 OFK라는 프로젝트는 확인되지 않았습니다. 또한 “바이크보딩”은 문맥상 바이브 코딩(vibe coding)을 뜻하는 것으로 해석했습니다. 이 가이드는 2026-07-25 발표된 OKF v0.2를 기준으로 합니다. Google Cloud 발표

관리되는 바이브 코딩의 한 문장 정의

사람이 의도와 승인 기준을 소유하고, AI는 경계가 정해진 작업을 수행한다.

빠르게 실험하되, 중요한 변경은 사양 → 계획 → 작업 → 구현 → 검증 → 지식 갱신의 흔적을 Git에 남깁니다. 채팅 기록은 보조 자료이고 저장소가 최종 기록입니다.

하나의 공통 원본, 세 개의 얇은 어댑터, 결정적인 CI가 핵심입니다. AI를 바꿔도 팀의 사양과 지식은 그대로 남습니다.

# Repository operating contract

## Read before changing code
1. Read `.specify/memory/constitution.md`.
2. Read the active feature's `spec.md`, `plan.md`, and `tasks.md`.
3. Follow links from `knowledge/index.md` only when relevant.

## Boundaries
- Never read or edit `.env*`, credentials, or generated vendor files.
- Do not add a production dependency without explaining why.
- Do not push, deploy, or merge unless the user explicitly asks.

## Definition of done
- Acceptance criteria are covered by tests.
- `npm run lint`, `npm test`, and `npm run build` pass.
- Report commands run and any remaining risk.

03

지침 파일은 “합쳐지는 문맥”입니다

설정 우선순위와 자연어 지침의 로딩 순서는 별개입니다. “하위 파일이 항상 상위 지침을 무효화한다”고 단순화하면 위험합니다.

바로 적용할 템플릿이 필요하신가요?

페이지 상단의 지침 팩은 아래 로딩 차이를 그대로 반영합니다. 전체 묶음 또는 Codex·Claude Code·Gemini CLI별 ZIP을 받은 뒤 각 README.md의 설치 순서를 따르세요. 대괄호로 표시된 프로젝트 명령은 실제 저장소에 맞게 채워야 합니다.

도구 주요 지침 경로 탐색·결합 방식 실제 확인
Gemini CLI ~/.gemini/GEMINI.md
저장소·하위 폴더 GEMINI.md 		전역 → 작업공간/상위 → 접근한 파일에 가까운 컨텍스트를 추가합니다. 기본 경계는 보통 .git입니다. /memory show, /memory refresh
Claude Code 관리형 → ~/.claude/CLAUDE.md → 루트/상위 CLAUDE.md → CLAUDE.local.md 넓은 범위에서 현재 폴더까지 이어 붙이고, 하위 폴더 지침은 해당 파일을 읽을 때 지연 로드합니다. /memory, /context, /status

04

설정 우선순위와 신뢰 경계를 분리합니다

설정 파일은 승인·샌드박스·MCP·Hook처럼 실제 실행 능력을 바꿉니다. 복제한 저장소의 설정을 읽지 않고 곧바로 trust하지 마세요.

높은 우선순위 → 낮은 우선순위

도구 설정 계층 핵심 주의
Gemini CLI CLI → 환경 변수/.env → 시스템 강제 → 프로젝트 → 사용자 → 시스템 기본 → 내장 시스템 기본과 강제 설정은 다릅니다. 문자열은 ${VAR:-fallback} 확장을 지원합니다.
Claude Code managed policy → --settings → .claude/settings.local.json → 프로젝트 → 사용자 객체·배열은 병합 규칙이 있으며 permissions는 병합 후 deny → ask → allow 순으로 판정합니다.
Codex CLI/-c → 중첩 프로젝트 config → profile → 사용자 → 시스템 → 내장 requirements.toml은 일반 override가 아니라 관리자 제약입니다. untrusted 프로젝트의 .codex/는 무시됩니다.
<repo>/.gemini/settings.json 
{
  "general": {
    "defaultApprovalMode": "default"
  },
  "security": {
    "environmentVariableRedaction": { "enabled": true }
  },
  "context": {
    "fileFiltering": {
      "respectGitIgnore": true,
      "respectGeminiIgnore": true
    }
  },
  "skills": { "enabled": true },
  "hooksConfig": {
    "enabled": true,
    "notifications": true
  }
}

{
  "security": {
    "folderTrust": { "enabled": true }
  }

Skills는 “매번 다시 설명하지 않을 절차”입니다

긴 규칙 파일 대신 필요한 순간에만 전체 내용을 불러옵니다. 이름과 description이 정확할수록 AI가 올바른 Skill을 고릅니다.

도구 프로젝트 경로 사용자 경로 호출 예
Gemini CLI .gemini/skills/, .agents/skills/ ~/.gemini/skills/, ~/.agents/skills/ /skills list, 요청과 description 일치
Claude Code .claude/skills/<name>/SKILL.md ~/.claude/skills/ /<skill-name> 또는 암묵 선택
Codex CWD→루트의 .agents/skills/ ~/.agents/skills/ $<skill-name>, /skills

Gemini Skill의 동일 이름 충돌은 낮은 범위부터 built-in → extension → user → workspace 순이며, 뒤의 더 높은 범위가 이깁니다. 팀 Skill은 고유한 이름을 사용해 의도치 않은 가림을 피하세요.

한 원본을 세 도구에 연결하는 현실적인 방법

.ai/skills/를 사람이 편집하는 단일 원본으로 사용

검토된 동기화 스크립트가 .agents/skills/에 Codex·Gemini 공용 설치 사본을, .claude/skills/에 Claude 설치 사본을 만듭니다. Gemini용 .gemini/skills/ 사본을 또 만들면 같은 이름을 중복 발견할 수 있으므로 이 전략에서는 만들지 않습니다. CI에서 두 설치 사본이 원본과 같은지 검사하세요.

.ai/skills/review-change/SKILL.md · 편집 원본 
---
name: review-change
description: 구현된 변경을 활성 Spec Kit 사양, 테스트, 보안 기준과 대조해 검토할 때 사용한다.
---

# Review change

1. 루트 `AGENTS.md`와 활성 기능의 `spec.md`, `plan.md`, `tasks.md`를 읽는다.
2. 현재 diff를 요구사항 ID와 연결한다.
3. 수용 기준별 테스트 존재 여부와 실제 결과를 확인한다.
4. 정확성, 보안, 호환성, 누락 테스트 순으로 발견 사항을 보고한다.
5. 근거가 없으면 성공을 선언하지 않는다.
6. 사용자가 수정을 요청하기 전에는 파일을 편집하지 않는다.

좋은 Skill과 나쁜 Skill

좋음

경계가 명확한 절차

“릴리스 후보 검증”, “DB 마이그레이션 리뷰”, “Spec 대비 diff 검토”처럼 시작 조건·입력·출력·완료 기준이 보입니다.

피하기

모든 일을 하는 만능 Skill

“최고의 코드를 작성한다”처럼 trigger가 모호하거나, 배포·삭제·전송을 암묵적으로 수행하는 Skill은 예측과 검토가 어렵습니다.

내용 Instructions에 둘 때 Skill에 둘 때
테스트 명령 항상 적용되는 짧은 명령 목록 여러 단계의 진단·재시도·증거 수집
보안 규칙 항상 금지되는 경계 보안 리뷰의 상세 체크리스트와 보고 형식
배포 “명시 승인 없이 하지 않음” 명시 호출 전용, 승인 지점이 있는 배포 절차
도메인 지식 매 작업에 필요한 한두 문장 참고자료·스크립트와 함께 쓰는 전문 워크플로

Claude는 부작용 있는 Skill에 disable-model-invocation: true를 둘 수 있습니다. Codex는 agents/openai.yaml의 policy.allow_implicit_invocation: false로 암묵 호출을 끌 수 있습니다. Gemini의 외부 Skill은 설치 전에 포함된 스크립트를 반드시 검토하세요.

MCP는 외부 시스템으로 나가는 문입니다

GitHub·문서·디자인·이슈 트래커를 연결할 수 있지만, 읽기와 쓰기의 위험이 다릅니다. 서버 정의는 공유하고 자격증명과 승인은 개인별로 유지합니다.

MCP 범위와 우선순위

도구 공유 프로젝트 설정 개인 설정 충돌 시
Gemini CLI .gemini/settings.json ~/.gemini/settings.json 일반 설정 계층에 따라 해석. Folder Trust가 켜진 상태에서 workspace가 untrusted이면 사용자 범위를 포함한 모든 MCP 연결을 시도하지 않음
Claude Code 저장소 루트 .mcp.json ~/.claude.json 같은 이름 전체 entry 기준 local → project → user → plugin
Codex .codex/config.toml ~/.codex/config.toml 일반 config 계층, 프로젝트 trust 필요

안전한 도입 순서

1. 처음에는 read-only 도구만

검색·조회·문서 읽기만 활성화하고 실제 도구 이름을 확인합니다.

2. 서버별 allow list

업무에 필요한 도구만 열고 delete/admin/publish 계열은 비활성화합니다.

3. 환경 변수로 자격증명 주입

설정에는 토큰 이름만 두고 값은 OS keychain·secret manager·CI secret에 둡니다.

4. 쓰기는 매번 승인

이슈 생성·댓글·push 같은 외부 변경은 초기에 수동 승인합니다.

5. 로그와 회수 경로 확인

어떤 계정으로 실행되는지, 토큰을 어떻게 폐기하는지 문서화합니다.

Gemini

/mcp list

/mcp schema로 도구 이름, /mcp auth로 인증 상태를 확인합니다.

Claude

/mcp

프로젝트 .mcp.json은 사용자 승인 후에만 실행됩니다.

Codex

/mcp

codex mcp list, OAuth 서버는 codex mcp login <server-name>으로 확인합니다.

하나의 저장소에만 필요한 기능은 repo-local 설정이 단순합니다. 여러 저장소나 팀에 설치 가능한 묶음이 필요할 때 Plugin/Extension으로 승격하세요.

세 도구의 패키지 형식은 서로 호환되지 않습니다

도구 명칭 필수 manifest 묶을 수 있는 것

Claude Code Plugin .claude-plugin/plugin.json Skills, agents, hooks, MCP, LSP, monitors, settings

저장소에 Plugin 소스가 있다고 자동 설치되지 않습니다.

각 개발자는 Plugin/Extension을 설치·활성화하고, 필요한 Connector/MCP 인증과 새 세션 시작을 수행해야 합니다. Codex의 workspace trust는 프로젝트 .codex 설정·Hook·Rule을 위한 경계이며 모든 Plugin의 공통 설치 승인이 아닙니다. Plugin에 묶인 Hook은 별도로 내용을 검토하고 신뢰해야 합니다. Codex Plugin 브라우저는 CLI와 데스크톱 앱에서 제공되며 IDE 확장에서는 지원되지 않습니다.

어떤 수단을 선택할까?

필요 선택 이유
한 저장소의 짧은 상시 규칙 Instructions 자동 로드, Git diff가 명확함
반복 절차와 참고자료 Skill 필요할 때만 전체 로드
외부 서비스의 데이터·행동 MCP 권한과 도구 경계를 서버 단위로 관리
여러 저장소·팀에 설치 Plugin / Extension 버전·구성요소·설치 경로를 패키지화
도구 호출 전후 자동 차단 Hook 자연어가 아니라 실행 시점에 강제
전문가 역할로 문맥 분리 Subagent 도구 범위와 대화 문맥을 분리

Subagent 사용 원칙

tasks.md 어떤 순서·파일·검증으로 나눌까? 범위와 병렬화 확인
코드·테스트·converge 결과 사양을 실제로 만족했나? PR 병합 전

빠른 실험과 프로덕션을 구분

작은 실험

specify → plan → tasks → implement

constitution이 이미 수립된 프로젝트에서, 버리는 프로토타입·내부 스파이크처럼 위험이 낮고 요구가 명확한 작은 변경에 적합합니다.

제품 변경

clarify·checklist·analyze·converge 포함

사용자 데이터, 인증, 결제, 공개 API, 마이그레이션, 큰 기능에는 품질 게이트를 생략하지 않습니다.

Spec Kit가 장기 지식 저장소를 대신하지는 않습니다.

기능별 spec/plan/tasks는 변경의 기록입니다. 여러 기능에서 반복 사용되는 아키텍처·결정·런북은 OKF knowledge/로 승격하고, spec에서는 해당 문서 링크만 참조하세요.

업그레이드 규칙

버전 PR에서만 실행

specify self upgrade --tag vX.Y.Z
specify version

specify integration upgrade codex
specify integration upgrade claude
specify integration upgrade gemini

git diff -- .specify .agents .claude .gemini

self check는 새 버전 존재 여부만 확인합니다. integration upgrade는 현재 설치된 CLI의 템플릿을 다시 적용할 뿐 CLI 자체를 올리지 않으므로, 목표 release tag로 CLI를 먼저 업그레이드하세요.

09

OKF v0.2로 “믿을 수 있는 지식”을 남깁니다

OKF는 플랫폼이나 SDK가 아니라 Markdown+YAML 규약입니다. 사람과 AI가 같은 파일을 읽고, 출처·검증·신선도를 판단할 수 있게 합니다.

Portable

그냥 Markdown

Git diff, GitHub 렌더링, 로컬 검색, 다른 AI 도구에서 모두 읽을 수 있습니다.

Minimal

개념 문서는 type만 필수

예약 파일인 index.md/log.md를 제외한 concept document 기준입니다. 알 수 없는 type·추가 key·끊어진 링크도 허용합니다.

Trust signals

출처와 검증을 분리

누가 만들었는지, 누가 확인했는지, 언제 낡는지를 frontmatter로 표현합니다.

번들 구조

knowledge/ ├─ index.md # 선택; 루트에서만 okf_version 가능 ├─ log.md # 선택; 날짜별 변경 기록, 최신순 ├─ architecture/ │ └─ system-overview.md ├─ decisions/ │ └─ adr-0001-authentication.md ├─ policies/ │ └─ security.md ├─ runbooks/ │ └─ local-validation.md └─ glossary/ └─ domain-terms.md

# Procedure

로컬에서도 CI와 동일한 검증을 실행한다.[^ci-workflow]

1. `npm run lint`
2. `npm test`
3. `npm run build`

[^ci-workflow]: Repository CI workflow
필드 의미 운영 해석
type 문서가 나타내는 개념 종류 OKF concept document에서 유일한 항상 필수 필드
sources 문서가 파생된 내부·외부 자료 각 항목의 resource는 필수
generated 현재 내용을 누가 언제 만들었나 AI 생성과 사람 작성 모두 actor convention 사용
verified 누가 언제 근거와 대조했나 human:<id>가 있으면 human-reviewed
status draft, stable, deprecated 생략 시 stable
stale_after 이 날짜부터 오래된 것으로 판단 자동 삭제가 아니라 재검토 신호
verified는 권한이 아닙니다.

신뢰를 판단하는 조언 신호일 뿐, 접근 통제나 보안 승인을 제공하지 않습니다. 실제 권한은 저장소 권한, MCP 승인, 샌드박스, CI와 조직 정책이 담당합니다.

언제 OKF로 승격할까?

정보 둘 곳 이유
이번 기능만의 수용 기준 specs/001-.../spec.md 변경 단위 기록
여러 기능이 따라야 할 인증 결정 knowledge/decisions/ 재사용, 출처, 재검토일 필요
매번 실행할 리뷰 절차 Skill 행동 순서가 핵심
항상 금지할 비밀 처리 AGENTS.md + Hook/CI 상시 지침과 결정적 강제 모두 필요
장애 대응 런북 knowledge/runbooks/ 여러 작업·사람이 반복 참조

Spec Kit 커뮤니티 목록에는 speckit_ofk라는 “OKF Knowledge Bundle Generator”가 있지만 설명상 v0.1 대상입니다. OFK는 이 독립 커뮤니티 확장의 slug 오탈자일 뿐 OKF의 대체 명칭이 아니며, Google 또는 Spec Kit가 보증하는 공식 OKF 구현도 아닙니다. 설치 전 최신 v0.2 호환 여부와 생성되는 trust 필드를 직접 확인하세요. Spec Kit 커뮤니티 확장 목록

이 HTML을 GitHub Pages에 게시하는 방법

이 가이드는 Jekyll 빌드가 필요 없는 정적 파일입니다. 가장 단순한 방법은 저장소의 /docs 폴더를 그대로 게시하는 것입니다.

방법 A · branch의 /docs 게시

1. 이 패키지의 docs/를 저장소 루트에 복사

docs/index.html, docs/assets/, docs/.nojekyll이 있어야 합니다.

2. commit하고 기본 브랜치에 반영

상대 경로를 사용하므로 프로젝트 Pages의 /repository-name/ 아래에서도 동작합니다.

3. GitHub → Settings → Pages

Build and deployment에서 Deploy from a branch를 선택합니다.

4. branch: main, folder: /docs

Save 후 배포가 완료되면 GitHub가 공개 URL을 표시합니다.

Pages는 공개될 수 있습니다.

저장소가 private이어도 요금제와 조직 설정에 따라 Pages 사이트는 인터넷에 공개될 수 있습니다. 이 HTML이나 연결 문서에 토큰·내부 URL·고객 데이터·사내 정책 원문을 넣지 마세요. GitHub 공식 게시 소스 문서

방법 B · GitHub Actions

빌드 과정이나 사전 검사가 필요하면 Settings → Pages에서 GitHub Actions를 선택하고, configure-pages, upload-pages-artifact, deploy-pages를 사용하는 workflow로 ./docs를 배포합니다. 함께 제공되는 예제 workflow를 저장소의 .github/workflows/pages.yml로 복사할 수 있습니다.

Pages Actions 예제 내려받기
.github/workflows/pages.yml 
name: Deploy guide to GitHub Pages

on:
  push:
    branches: [main]
    paths: ["docs/**", ".github/workflows/pages.yml"]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/configure-pages@v6
      - uses: actions/upload-pages-artifact@v5
        with:
          path: ./docs
      - name: Deploy
        id: deployment
        uses: actions/deploy-pages@v5
